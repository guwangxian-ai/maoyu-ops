# 账号商品同步与查询

## 数据来源与入口

“本地商品”指本项目数据库中的记录；项目部署到服务器后，这些仍是系统保存的副本，并不变成闲鱼的实时数据。

| 入口 / MCP 工具 | 数据来源和作用 |
| --- | --- |
| 商品管理「获取商品」 / `items_fetch_all_items_from_account`，传 `body.cookie_id` | 从指定账号的闲鱼在售列表翻页拉取，新增/更新本地商品记录 |
| 商品管理「获取所有账号商品」 / 同一工具，不传 `body.cookie_id` | 同步当前权限范围内所有账号，返回各账号执行汇总 |
| `items_fetch_items_from_account` | 只拉取指定账号的一页并入库，不能据此声称已查全 |
| `items_list_items`、`items_list_items_paginated`、`items_list_items_by_cookie`、`items_get_item_detail` | 读取本地数据库，调用成功不代表已请求闲鱼或数据最新 |
| `search_search_items` / `items_search_items` | 搜索闲鱼市场商品用于选品，不同步自己店铺，也不能代替本人商品查询 |

同步接口在当前 MCP 中属于 `xianyu:read`：读取平台并更新系统副本，不上架、改价、下架或删除平台商品。它是用户要求查询当前商品的正常步骤，无需为同一查询另行请求“允许同步”。用户明确要求离线或只查本地时遵从其范围。

## 查询顺序

1. **确定账号和目标。** 使用 `account_list_cookie_options` 的 `id` 作为 `cookie_id`，不要传 `pk`。明确账号时只同步该账号；用户要求全部账号或全店查找时覆盖对应范围。可以先读本地记录定位账号/商品 ID，但此时不作平台状态结论。存在同名商品时以账号和商品 ID 区分。
2. **取得本次平台数据。** 先发现实际 schema，再调用 `items_fetch_all_items_from_account`。需要完整查询时不要设置 `max_pages`；一页、受页数限制或定时增量任务的旧结果不能替代完整同步。已完成的本次同账号完整同步可以在紧接着的查询中复用；发布、改价、编辑、下架等变更后重新核对，隔一段时间的新查询也应重新同步。
3. **检查真实完成情况。** 按下面的规则检查账号覆盖、失败、跳过及保存数量，并保存本次响应和接收时间。`doctor` 成功、账号已登录、页面刷新、数据库 `created_at` 都不是商品同步完成证据。
4. **结合平台列表和本地配置查商品。** 单账号完整同步响应的 `items` 是本次拉取的在售商品；其中的商品 ID 通常在 `id`。先在这份结果中核对目标是否出现及平台返回字段，再用本地列表/详情读取卡券、回复等系统配置。查询本地分页时继续到结束或定位到明确 ID，不能用第一页空结果判断全库没有。
5. **注明结论范围。** 报告账号、查询时间、同步范围与结果，以及目标来自“本次平台返回”还是“本地历史记录”。已过时/未取得的价格、库存或状态标为未确认，不补猜。

典型参数（具体账号用真实返回值替换；这些示例不执行业务）：

```json
{"body":{"cookie_id":"实际账号ID","page_size":20}}
```

上面用于单账号完整同步。「获取所有账号商品」使用同一工具：

```json
{"body":{"page_size":20}}
```

同步后查本地，调用 `items_list_items_paginated`：

```json
{"query":{"cookie_id":"实际账号ID","keyword":"目标商品ID或名称","page":1,"page_size":20}}
```

## 同步成功不只看一个 success

- **单账号**：要求业务 `success=true` 且没有 `skipped=true`。锁被占用时接口可能返回 `success=true, skipped=true, total_count=0`，这表示本轮没执行，不能解释为“这个账号没有商品”。等待已有同步结束后再核对，避免密集重试。
- **保存不完整**：对比 `saved_count` 与 `total_count`。前者包括已存在且保存成功的商品，并非只统计新增商品；明显少于抓取数量说明有记录未成功进入本地库。可以报告本次平台确实返回的条目，同时说明本地未完整更新，不能声称完整同步。
- **所有账号**：顶层 `success=true` 可能仍有 `failed_account_count>0`，需逐项检查 `results/failed_accounts/message`，确认目标账号实际覆盖。当前汇总结果不包含各账号完整商品列表，也未完整透传单账号 `skipped` 字段。需要确认某个商品是否仍在售，或某账号返回零条但提示跳过时，单独同步该账号，取得明确结果再判断。
- **返回文件句柄**：通过 `mcp_read_file` 读取完整 JSON 后再检查，不把句柄或截断输出当作已查全。
- **失败/过期/风控**：说明具体原因；本地结果只能标作历史数据。目标状态不明时暂停依赖该状态的发布、改价、删除、绑定等动作，不拿旧数据填补成功结论。

同步响应通常直接含 `success/items/total_count/saved_count` 等字段，而非统一放在 `data` 内。脚本会再包装一层 `result`。按真实返回结构读取；完整 API 参数仍以实时 schema 为准。

## 本地存在和平台存在分别判断

- **本地没有，本次平台返回有**：商品已在本次闲鱼在售列表出现。核对账号、关键词、分页及入库结果，不能再上架一份来“修复缺失”。
- **本地有，本次平台返回没有**：只说明它未出现在本次该账号的在售列表。现有同步按返回内容新增/更新，不会统一清除未返回的本地旧记录；不能直接断言仍在售、已删除、已售出或下架。
- **完整同步后仍未找到**：可说“本次该账号在售列表中未找到”。列表只覆盖在售，不能据此推断从未发布或所有状态下都不存在；用平台明确支持的详情/状态查询或用户提供的页面证据进一步核实。鱼小铺可按能力使用 `items_get_seller_item_edit_detail` 辅助查看平台详情，但详情可读取也不等于证明在售。
- **只查本地**：回答“本地记录显示……，本次未同步闲鱼，平台当前情况未核验”。不得自动从本地查询升级为外部写入。

## 对后续流程的影响

上架前去重、编辑/下架前核对、商品卡券绑定都沿用上述规则。查询不到不是发布授权，商品已在闲鱼发布而入库延迟时只补同步，不重复发布。

本地编辑不会修改闲鱼；后续同步可能覆盖本地的平台字段。本地删除也不代表闲鱼下架/删除，平台仍有的商品可能重新入库，但被清理的卡券关联不会自动恢复。平台下架保留本地记录，因此本地仍能查到也不代表还在售。实际操作选择及平台删除后本地清理失败的处理见 [商品操作与上架](listing.md)。

订单关联的商品可能已经售出或下架，因此不能要求它必须仍在在售列表才能核对历史订单；使用订单携带的商品 ID、账号、规格及独立订单状态证据。商品同步不能证明订单已付款或卡券已送达。
