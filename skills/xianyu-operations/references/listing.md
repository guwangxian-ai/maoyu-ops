# 商品操作、草稿与上架

新发布、重发或变更商品内容前，按 [商品合规与处罚处理](compliance.md) 完成准入和实际交付核对；已有处罚或高风险未确认时先停在草稿，不用真实发布试审核。开源、低价、付款后发货和本节文案约定不能代替平台允许交易的依据。仅改价/库存且没有新风险信号时可复用同版本有效记录。

## 先选择正确操作

| 目标 / MCP 工具 | 实际作用和结果边界 |
| --- | --- |
| 本地编辑：`items_update_item` | 修改本系统数据库，不向闲鱼修改标题、描述、价格等平台字段。保存成功只能报告“本地已更新”。 |
| 鱼小铺平台编辑：`items_update_seller_item` | 向闲鱼原商品 ID 提交编辑，成功后尝试同步账号商品；平台编辑成功和本地同步成功分别核对。 |
| 鱼小铺改价、库存：`items_update_item_price` | 向闲鱼原商品提交价格与库存；单规格一起提交 `price/quantity`，多规格提交 `skus`。先读取当前规格与库存，保留未授权修改的值。 |
| 平台下架：`items_batch_offline_items` | 停止闲鱼售卖，保留本地商品记录及卡券关联；接口不更新本地记录，下架不能报告成删除。 |
| 本地删除：`items_delete_item_unified`、`items_delete_item`、`items_batch_delete_items` | 只删除本地商品及卡券关联，不下架、不删除闲鱼商品，也不删除卡券本身。平台仍存在的商品可能在后续同步时再次入库，已清理的卡券关联不会因此自动恢复。 |
| 平台删除：`items_batch_delete_xianyu_items` | 删除闲鱼商品；平台成功项再清理本地商品及卡券关联，平台失败项保留。不会删除卡券本身。本地清理可能单独失败，须查回执。 |

用户说“修改”时明确目标是否为闲鱼公开商品；说“删除”时结合上下文区分本地清理、停止售卖、平台删除。已有明确授权沿用；仍有歧义才询问，不按按钮名猜。平台删除需要目标商品在所选账号的本地记录中存在以校验归属，先按 [账号商品同步与查询](catalog-sync.md) 核对，不能先删本地再用平台删除工具。

### 平台修改的能力与回读

1. `account_get_publish_account_capability` 核对目标账号实际能力；两个平台修改工具仅支持鱼小铺，不能拿普通账号调用失败后改用本地编辑冒充成功。代码提供了平台编辑能力，不等于当前账号和本次变更已验证成功。
2. 编辑前读 `items_get_seller_item_edit_detail` 的平台详情，再构造 `items_update_seller_item` 完整表单。该接口是全量提交，服务端会再次读取平台快照；按实时 schema 保留未修改字段，不能只发送标题等增量并依赖默认值。素材、规格、发货设置须与当前详情及授权一致。
3. 查实际业务 `success/message`，再回读平台详情/本次同步结果确认修改字段和原商品 ID；本地 `items_get_item_detail` 不能单独证明平台修改。同步失败或被跳过时单独恢复同步，不重做已确认的外部编辑。当前详情若不含状态证据，不能据此宣称在售。

### 下架、删除的逐项验收

- 下架查看 `data.results/suc_count/fail_count`；平台删除查看 `data.results/success_count/fail_count`。顶层成功可以包含部分失败，逐商品记录平台结果；超时或结果不明先查状态，不对整批重复提交。
- 平台删除另看 `data.local_deleted_count/local_failed_ids`。平台已删除而本地清理失败时，只恢复这些 ID 的本地清理，不再调用平台删除；保留平台成功回执。平台失败项继续保留本地商品，不能顺手清掉。
- 分别报告“本地记录已删除”“闲鱼已下架”“闲鱼已删除”“卡券关联已清理”和未完成项。删除商品关联不代表删除卡券内容或处理历史订单。

## 公开商品文案约定

本项目用户于 2026-10-21 明确要求：商品页不添加各种外链，描述简短、自然。此为本项目经营约定，其他用户或实例按其要求处理；不承诺按此写法一定不会被审核或下架。

- 标题、描述和公开图片不展示网址、域名或外部入口，包括作者主页、GitHub、官方站点、下载和网盘分享。也不改成二维码、拆字、谐音或联系方式引导外跳。API 图片地址等媒体字段仍按接口要求保留；私有来源记录、研究引用和给店主的操作回执不属于公开商品文案。
- 通常用 3–5 句说清“是什么、包含什么、必要使用条件、付款后如何交付”。能更短就更短，通常不超过约 150–200 字；不凑字数，不堆分区标题、促销套话、重复介绍或长篇免责声明。价格和配置以实际商品为准，保留影响购买决定的限制与真实售后边界，不编造兼容性、授权或效果。
- 软件免费开源时如实写明；收费对应教程、整理或其他实际交付价值，不包装成官方收费授权。作者或项目名可用纯文字说明。按许可证在交付包内保留版权声明、许可证、对应源码和来源地址；商品页不放链接不等于删除这些文件。若某许可另有必须公开展示的要求，先处理该要求与本约定的冲突，不能静默省略。
- 采用付款后交付的商品，只在商品页说明“付款后通过夸克交付”等实际方式，不放链接、提取码或免费领取口令。实际地址继续保存在原卡券并由已确认付款的订单流程交付，不能为精简文案改成售前发链接。
- 发布、编辑或重发前，检查将实际提交的标题、描述和每张公开图片；有对应素材时一并更新过时文案，避免从旧素材或发布日志恢复链接和长文。只改用户授权的文案字段，保留原价、库存、图片、规格及发货关联；媒体图片需要调整时另按实际授权处理。提交后从平台回读核对，素材保存不能代替平台编辑结果。

## 虚拟商品售后与发货承诺

2026-10-23 店主明确要求：本项目虚拟商品默认“不满意包退、下单秒发货”。这是本店已批准的经营承诺，后续在已授权的发布、编辑和重发范围内直接沿用，不重复确认同一售后文案，不套用到其他店主或实例。

- 推荐短句：“不满意包退，付款后自动秒发，夸克网盘交付。”网盘名称按实际卡券填写；“下单”始终指成功付款，未付款不发链接或提取码。不添加未经批准的价格、折扣、退款期限或“仅未下载可退”等限制，也不保留“虚拟商品不退不换”“发货后不退”等冲突文案。
- 使用“秒发货”前核对账号启用、独立 WebSocket 发货连接、自动发货开关，以及商品对应的启用卡券、规格匹配和分享可用性。具备自动交付能力时可使用店主指定措辞；不能凭卡券存在就断言实时已送达，也不编造固定秒数、零延迟或永不故障的保证。发现离线、失效链接、人工交付等具体问题时先处理授权内可修复项；仍不能自动发货的商品保留“不满意包退”，如实说明发货方式和未完成项，不能虚构秒发能力。
- 售后询问用简短回复说明“不满意可以在闲鱼订单申请退款，按平台流程处理”；不得以虚拟商品为由否定本店承诺。买家说未收到时核对原订单与发送回执，不能在售前聊天补发链接，也不能声称钱已退回或另设站外退款渠道。
- 公开描述、商品 AI 提示词、默认回复、对应素材和复用发布草稿保持一致；保留产品事实、使用限制、开源说明、价格、库存、媒体和原卡券绑定。退款文案约定不等于已开启自动退款，不授权取消或退款任意历史订单；具体订单操作按用户已批准范围和平台工具核验。

## 可重复交付虚拟商品的库存

本项目用户于 2026-10-20 约定：已获准发布且能重复交付的虚拟商品，采用当前账号、分类和接口实际支持的最大可售库存，不再默认 1 件；用户明确指定数量时从其要求。此约定只决定已授权商品的库存，不授权新选品发布、批量修改其他在售商品或自动续售。技能用于其他用户或实例时，先读取其经营约定，不把本项目偏好直接套用到他人店铺。

1. 先读 `account_get_publish_account_capability`，确认 `is_fish_shop` 与 `support_sku_or_inventory`。普通账号或不支持多库存时，不静默退回 1 件后报告完成；说明当前能力限制，不自行启用自动重发。
2. 核对实时 schema 和当前接口限制。2026-10-20 的项目 `quantity` 上限为 `999999`，已在一次鱼小铺单规格发布中被平台接受并回读确认；这是当前接口及已验证账号的证据，不是所有账号、分类的统一平台上限。若该账号/分类已有明确更低上限，按有效上限提交；只有平台明确拒绝、确认未创建商品后，才按其具体限制修正参数并登记新操作，不能靠反复公开发布试探上限。
3. 单规格发布显式填写 `quantity`；兼容字段 `stock` 若一并传入，须与其一致。不能只填 `stock` 而让实际载荷的 `quantity` 留在默认 1，也不能将旧的“虚拟物品建议 999”字段提示当作平台最大值。多规格保持原规格及定价，按各 SKU 与总库存限制填写，不凭空增加规格或把每个 SKU 都设为单品上限。
4. 大库存适用于可重复交付、拥有相应分发权限的资料。一次性卡密、授权席位或人工服务数量按真实可交付数量约束。可售库存不等于单笔发货份数，不能把 `quantity=999999` 写成卡券的 `delivery_count`；仍按实际订单与原卡券规则交付。
5. 本次发布使用已有素材时，同步该素材的 `quantity` 及过时的数量备注，避免下次从旧草稿恢复成 1 件；保留价格、文案、图片及其他配置。写入后回读素材数量。平台商品还须按下文核验实际库存，素材保存成功不能替代平台结果。

## 修改或售罄后重新发布

当前没有通用的“一键编辑 = 下架重发”接口。“修改文案”“改价”“补库存”本身不包含重发授权；鱼小铺原商品仍在售时优先按已授权范围修改原商品。用户明确要求重发时，区分仍在售和已售罄两种情况。项目另有成交后自动续售配置，一次重发不等于开启持续自动续售。

获准后按以下顺序处理：

1. 同步并确认账号、旧商品及当前状态；读取平台详情、当前素材、完整卡券/规格关联、商品 AI 提示词和默认回复，保存旧 `item_id` 及这些配置。售罄判断不能只看它从在售列表消失；结合平台库存为 0、订单及明确状态证据，区分售出、手动下架和状态未明。
2. 先确认该账号可发布、所需表单/素材完整、原分享可访问，再按上述库存约定准备参数。旧商品仍在售时，须已有下架授权并核对下架成功后再发；已确认售罄且不在售时，不额外下架或删除旧商品。状态不明时停止依赖该状态的发布。
3. 按下文发布流程和稳定操作编号创建新商品，保存新的 `item_id/item_url/log_id`。中断或只缺同步时先查已有发布回执，不能再次发布一份。
4. 用 `cards_update_item_cards` 为新商品绑定已核对的原卡券，保留规格及旧商品关联。通过 `items_save_item_ai_prompt` 和 `items_save_item_default_reply` 迁移该商品当前生效的回复配置，将提示词中的旧商品 ID 精确改为新 ID，保留启用、回复次数等设置。仅迁移本次授权涉及的商品规则，不修改账号全局设置。
5. 保留原商品已批准的交付条件。采用付款后交付的商品，描述、默认回复和 AI 提示词须一致；售前回复不含网盘链接或提取码，不能从旧发布日志恢复已经停用的免费领取规则。已有有效分享和卡券直接复用，不因重发重复上传或重新分享。
6. 同步核对新商品在售、价格及实际库存；分别回读卡券关联、AI 提示词、默认回复和素材数量，检查商品 ID 与启用状态。按 [网盘与卡券](delivery-assets.md) 核验发货账号及独立 WebSocket 状态；配置通过不等于已验证新商品的真实订单送达。
7. 记录旧 ID → 新 ID → 素材 → 卡券与回复配置的对应关系。旧订单继续对应原商品 ID，不迁移历史订单；浏览量、收藏、销量、评价是否延续没有保证。分别报告平台发布、库存、卡券和回复配置的结果；失败从已确认阶段恢复，不删除旧记录或重发整个流程。

## 虚拟商品默认全账号发布

2026-10-23 店主明确要求：本项目已获准发布的虚拟商品，默认发布到当前用户已连接的全部闲鱼账号。用户明确指定某个账号或排除账号时从其要求；此约定只决定发布任务的账号范围，不授权新选品、全店改价/编辑、重新启用停用账号或持续后台发布，也不套用到其他店主。

1. 每轮从 `account_list_cookie_options` 枚举完整账号范围并保存快照，不能写死账号名单或只选第一个在线账号。管理员可见的其他用户账号不自动属于本店。逐账号核对发布能力、完整在售同步、已有发布日志和操作回执；“获取商品”只同步列表，不会跨账号发布。
2. 建立“商品/资料版本 × 目标账号”清单，分别标记已有同款、待发布、待登录、已发布待绑定、已验收或失败。同款先比对资料版本、卡券、现有商品及历史映射，不能只凭标题变化新建。目标账号已在售同款时复用其 ID；完整同步仍不能确认旧商品状态、存在未知发布回执或相关处罚时，先核实，不把缺少列表记录当成补发依据。跨账号补齐不包含恢复历史下架/受罚商品。
3. 每个缺失且可发布的组合使用独立、稳定的 `operation_id`，记录来源账号/商品、资料版本、目标账号及新商品 ID；按各账号真实能力使用最大可售库存，价格与交付范围沿用已批准版本，公开图文仍遵守本文件。异步批量工具是笛卡尔积；不同账号的缺失清单不一致时分组或逐件执行，不能重复发布已有组合。
4. 新 ID 分别绑定相同资料版本的有效卡券、商品 AI 提示词与默认回复，精确替换回复里的旧 ID；保留原商品和历史订单关联。可复用固定文本卡券及有效分享，不为跨账号铺货重复上传或重建分享。一次性卡密和席位不能按可重复交付文本卡券处理。
5. 账号在线标志、发布接口可用、独立发货连接是不同证据。离线时查实际能力，不能擅自启用停用账号或声称秒发正常；登录/验证码需要用户参与。一个账号失败不撤销其他账号的成功，也不能静默跳过后报告“全部完成”。保留失败原因和已完成阶段；上线后先读原回执及平台状态，再续做未完成组合，不重发整个批次。当前普通发布没有“账号上线自动补发”队列，记录待续不等于已安排自动重试。
6. 完成时逐账号核对平台在售、实际库存、卡券唯一匹配、商品回复和发货能力，给出各账号已有/新增/失败/待处理数量。配置完成与真实订单送达分别报告。新增账号在下一次获准发布时重新纳入范围，不自动复制历史全店商品。

## 准备

查询 `account_get_publish_account_capability`，`path.account_id` 使用账号列表的 `id`。按鱼小铺/普通账号真实能力选择规格、库存等字段；授权失效时先恢复登录。

按上文公开商品文案约定，准备用户可审查的标题、描述、价格、数量、规格、交付说明、售后承诺和自有/获授权图片。数字资料先完成 [网盘与卡券](delivery-assets.md) 的交付检查。资料尚未准备好时只保留草稿。

- `publish_recommend_category` 返回平台分类/属性，以实时 schema 和结果填写，不猜分类 ID。
- 从 `personal_address_list_personal_addresses` / `address_list_publish_addresses` 读取本人真实地址；没有地址或平台要求人工确认时请用户补齐，不编造地点。
- 图片先用 MCP 暂存，再调 `publish_upload_product_images`；使用返回的允许路径/URL。上架接口不能用本机文件路径。不要为单纯测试公开上传无关图片。
- 部分历史 schema 将 `images` 描述为“图片本地路径列表”，但 MCP 另有媒体访问校验：这里使用业务上传后返回的 `/static/uploads/...` 或允许的闲鱼/阿里 HTTPS CDN 地址，不能传 AI 所在电脑的绝对路径。暂存的 `upload_id` 也须先经过业务图片上传，不能直接放入 `images`。
- `publish_create_material` 是本站草稿写入，仍需合法图片等完整参数。资料不全可以保存本地草稿 JSON，不用假的图片路径凑成功。
- `shipping_method` 以 schema 支持的 `free/distance/fixed/template/none` 等实际值为准，`none` 对应现有实现的自提；不存在可随意填写的 `digital` 值。按平台分类和商品实际交付方式设置，不能自动把虚拟商品伪装成实物/自提。

## 发布

发现 `publish_publish_single` schema，校验完整 payload。常见必填为 `account_id/title/description/price/images`；schema 只校验结构，不能证明分类、素材、库存和平台规则正确。用户只要求草稿/只读测试时停在本地草稿与参数预览。

已有授权应明确账号、商品草稿版本、价格/数量和发布数量上限；缺少授权时展示这个具体草稿再请求。首次真实发布宜一条：

1. 先按 [账号商品同步与查询](catalog-sync.md) 同步目标账号，结合本次平台列表与本站发布日志检查重复商品/相同业务操作。本地没有记录不能证明闲鱼未发布，同步失败不能作为重新上架的依据。
2. 使用 [执行与恢复](execution.md) 中的稳定编号执行 `publish_publish_single`。
3. 保存响应的 `item_id/item_url/log_id/sync_status/sync_message`。
4. 若取得 `item_id` 但 `sync_status` 失败，商品可能已经上架，只补查/同步该商品，不要再次 publish。
5. `items_get_item_detail`（`path.cookie_id`、`path.item_id`）读取本地库。先确认发布后的同步实际完成，再用本次平台列表核对归属、标题、价格、`quantity` 及在售状态；鱼小铺可再用 `items_get_seller_item_edit_detail` 核对实际库存。保存请求数量与平台回读数量；只回读到 1 件或未取得库存时，不能宣称最大库存发布完成。缓存中暂无商品时只补同步，不能把本地同步失败说成外部未发布。
6. 商品真实存在且交付内容已验证后，按已批准范围绑定卡券、配置商品回复，再读取关联与配置结果；重发按上节恢复原有规则。
7. 按下节核验该账号自动擦亮和目标商品结果，分别报告开关、资格及实际擦亮，不能把发布成功视为擦亮成功。

## 发布后擦亮核验

自动擦亮是账号级开关 `auto_polish`，不是 `publish_publish_single` 的商品参数。已有开启授权时直接沿用；新任务只核验现状，不把发布授权扩大为开启账号所有商品的后台任务。

1. 读取 `account_list_cookie_details_paginated` 的 `enabled/online/auto_polish`。已获准开启时用 `account_update_account_auto_polish` 写 `body.auto_polish=true`，保存稳定操作回执并回读。不要为了“核验”关闭再开启，也不要改动发货、AI 或密钥期限。
2. 发布后做完整成功同步，检查 `snapshot_complete/state_updated`。仅 `sale_status=on_sale` 且 `is_polished=false/null` 的商品进入任务；`unchecked/pending_verification` 保留但不擦亮。局部详情和发布自动保存不一定完成全账号快照，不能据此认为已经具备资格。
3. 用 `items_list_items_paginated` 的账号、商品关键字和状态筛选，或本地详情读取 `is_polished/polish_status/polish_checked_at`。`polish_status=success` 表示平台擦亮成功或平台确认今日已擦亮；结合时间和当日 `is_polished` 判断。北京时间跨日会重置标志，旧时间不是今日成功证明。
4. `auto_polish=true` 只证明配置；需要等实际 Scheduler 周期，短时有界查询。缺少当次结果时报告“已开启，等待执行/实际结果未确认”，不能编造完成时间。持续失败时检查平台登录、调度与管理员擦亮日志；MCP 不提供管理员日志/强制触发工具，不能伪造调用。没有长期监控授权时不无限轮询。
5. 平台返回 `UNSUPPORTED_ITEM_STATUS` 或“已下架商品不支持该操作”时，任务保留原商品、卡券、AI/默认回复与历史，标为 `pending_verification`，原因 `sale_verification_reason=polish_unsupported_status`；`polish_checked_at` 记录本次证据，`sale_checked_at/last_seen_at/sync_id` 仍是原完整同步时间。网络/登录失败不改变在售快照。请求期间出现更新的完整同步时不以旧失败覆盖新快照。待核实不能直接判为违规/售罄或据此重发。
6. 后续完整同步重新返回商品会恢复 `on_sale`；未返回仍待核实。修复或启用擦亮不要求删除本地商品、解绑卡券、重建 AI 回复，也不自动重新上架旧商品。

## 素材、地址、AI 上架与自动重发

素材通过 `publish_list_materials/get_material/create_material/update_material` 维护；删除/批量删除另有权限和范围，不能因发布失败清空原素材。图/视频使用各自业务上传工具，素材 ID 与平台商品 ID 分开记录。

`personal_address_*` 维护本人地址，可导入/导出；`address_*` 查询公共发布地址、账号选项和地点提示。先查已有项，修改/导入后回读，核对真实地点和所属用户。公共地址维护未开放 MCP，不将地点提示当作已保存的地址。

AI 上架先 `ai_listing_list_configs` 核对已存在配置和费用范围，创建后查 `ai_listing_get_task/list_tasks`。取消任务不代表已产生的素材或商品被撤销；按任务的真实产物逐项核对。模型凭证和配置维护见[后台边界](project-admin.md)。

自动重发用 `publish_get_auto_relist_rule` / `publish_save_auto_relist_rule`，事件用 `publish_list_auto_relist_events` / `publish_list_all_auto_relist_events`。规则写入、`publish_reconcile_auto_relist_event` 和 `publish_mark_auto_relist_event_failed` 需 `xianyu:automation:write` 及持续重发授权。先看原规则、事件和平台状态；状态未知先对账，不把标失败当取消平台商品，不并行手动重发和后台重发。普通账号重新上线没有通用发布补偿队列，不保证离线时失败的普通发布会自动补上。

## 批量

`publish_publish_batch` 的 `account_ids × material_ids` 是组合发布，先算总数量和重复风险，不能把两个数组误以为一一配对。沿用授权数量上限，返回 `batch_id` 后用 `publish_get_batch_status` 查询每条结果。成功的商品逐条保存并跳过；部分失败时不重发整个批次。

`ai_listing_create_task` 可能使用站内配置的付费模型。只有费用和范围已批准时才选它；当前 AI 已生成草稿时可以直接用基础素材/发布工具。

验收分别报告：草稿已保存、平台商品已生成、实际库存与在售状态已核验、本地同步已完成、卡券及商品回复已核验。只报告有证据的阶段，不将发布回执合并为一句“全部上架成功”。
