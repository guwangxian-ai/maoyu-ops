# 商品操作、草稿与上架

## 先选择正确操作

| 目标 / MCP 工具 | 实际作用和结果边界 |
| --- | --- |
| 本地编辑：`items_update_item` | 修改本系统数据库，不向闲鱼修改标题、描述、价格等平台字段。保存成功只能报告“本地已更新”。 |
| 鱼小铺平台编辑：`items_update_seller_item` | 向闲鱼原商品 ID 提交编辑，成功后尝试同步账号商品；平台编辑成功和本地同步成功分别核对。 |
| 鱼小铺改价、库存：`items_update_item_price` | 向闲鱼原商品提交价格与库存；单规格一起提交 `price/quantity`，多规格提交 `skus`。先读取当前规格与库存，保留未授权修改的值。 |
| 平台下架：`items_batch_offline_items` | 停止闲鱼售卖，保留本地商品记录及卡券关联；接口不更新本地记录，下架不能报告成删除。 |
| 本地删除：`items_delete_item_unified`、`items_delete_item`、`items_batch_delete_items` | 只删除本地商品及卡券关联，不下架、不删除闲鱼商品，也不删除卡券本身。平台仍存在的商品可能在后续同步时再次入库，已清理的卡券关联不会因此自动恢复。 |
| 平台删除：`items_batch_delete_xianyu_items` | 删除闲鱼商品；平台成功项再清理本地商品及卡券关联，平台失败项保留。不会删除卡券本身。本地清理可能单独失败，须查回执。 |

用户说“修改”时明确目标是否为闲鱼公开商品；说“删除”时结合上下文区分本地清理、停止售卖、平台删除。已有明确授权沿用；仍有歧义才询问，不按按钮名猜。平台删除需要目标商品在所选账号的本地记录中存在以校验归属，先按 [账号商品同步与查询](catalog-sync.md) 核对，不能先删本地再用平台删除工具。

### 平台修改的能力与回读

1. `account_get_publish_account_capability` 核对目标账号实际能力；两个平台修改工具仅支持鱼小铺，不能拿普通账号调用失败后改用本地编辑冒充成功。代码提供了平台编辑能力，不等于当前账号和本次变更已验证成功。
2. 编辑前读 `items_get_seller_item_edit_detail` 的平台详情，再构造 `items_update_seller_item` 完整表单。该接口是全量提交，服务端会再次读取平台快照；按实时 schema 保留未修改字段，不能只发送标题等增量并依赖默认值。素材、规格、发货设置须与当前详情及授权一致。
3. 查实际业务 `success/message`，再回读平台详情/本次同步结果确认修改字段和原商品 ID；本地 `items_get_item_detail` 不能单独证明平台修改。同步失败或被跳过时单独恢复同步，不重做已确认的外部编辑。当前详情若不含状态证据，不能据此宣称在售。

### 下架、删除的逐项验收

- 下架查看 `data.results/suc_count/fail_count`；平台删除查看 `data.results/success_count/fail_count`。顶层成功可以包含部分失败，逐商品记录平台结果；超时或结果不明先查状态，不对整批重复提交。
- 平台删除另看 `data.local_deleted_count/local_failed_ids`。平台已删除而本地清理失败时，只恢复这些 ID 的本地清理，不再调用平台删除；保留平台成功回执。平台失败项继续保留本地商品，不能顺手清掉。
- 分别报告“本地记录已删除”“闲鱼已下架”“闲鱼已删除”“卡券关联已清理”和未完成项。删除商品关联不代表删除卡券内容或处理历史订单。

## 普通商品修改后重新发布

当前没有通用的“一键编辑 = 下架重发”接口。确需此方案时，用户或已批准运营规则必须覆盖旧商品下架和新商品发布；“修改文案”“改价”本身不包含重发授权。项目另有成交后自动续售配置，它不是商品编辑流程，不能为一次修改自行开启。

获准后按以下顺序处理：

1. 同步并确认账号、旧商品及当前状态；保存来源草稿、旧 `item_id`、素材版本和完整卡券/规格关联配置，不能只保留可能被覆盖的本地记录。
2. 先确认该账号可发布、所需表单/素材完整、网盘交付与卡券已准备好，再下架旧商品。逐项保存下架回执，失败或状态不明的旧商品停止后续发布。
3. 按下文发布流程和稳定操作编号创建新商品，保存新的 `item_id/item_url/log_id`。中断或只缺同步时先查已有发布回执，不能再次发布一份。
4. 将已核对的卡券与规格配置重新绑定到新商品，再同步、回读新商品及关联结果。旧订单继续对应原商品 ID，不迁移历史订单；浏览量、收藏、销量、评价等历史数据是否延续没有保证。
5. 分别报告旧商品下架、新商品发布、新 ID、同步和卡券关联情况。失败停在已确认的阶段，不自动删除旧商品、重新上架旧商品或重发整个流程。

## 准备

查询 `account_get_publish_account_capability`，`path.account_id` 使用账号列表的 `id`。按鱼小铺/普通账号真实能力选择规格、库存等字段；授权失效时先恢复登录。

准备用户可审查的标题、描述、价格、数量、规格、交付说明、售后承诺和自有/获授权图片。数字资料先完成 [网盘与卡券](delivery-assets.md) 的交付检查。资料尚未准备好时只保留草稿。

- `publish_recommend_category` 返回平台分类/属性，以实时 schema 和结果填写，不猜分类 ID。
- 从 `personal_address_list_personal_addresses` / `address_list_publish_addresses` 读取本人真实地址；没有地址或平台要求人工确认时请用户补齐，不编造地点。
- 图片先用 MCP 暂存，再调 `publish_upload_product_images`；使用返回的允许路径/URL。上架接口不能用本机文件路径。不要为单纯测试公开上传无关图片。
- 部分历史 schema 将 `images` 描述为“图片本地路径列表”，但 MCP 另有媒体访问校验：这里使用业务上传后返回的 `/static/uploads/...` 或允许的闲鱼/阿里 HTTPS CDN 地址，不能传 AI 所在电脑的绝对路径。暂存的 `upload_id` 也须先经过业务图片上传，不能直接放入 `images`。
- `publish_create_material` 是本站草稿写入，仍需合法图片等完整参数。资料不全可以保存本地草稿 JSON，不用假的图片路径凑成功。
- `shipping_method` 以 schema 支持的 `free/distance/fixed/template/none` 等实际值为准，`none` 对应现有实现的自提；不存在可随意填写的 `digital` 值。按平台分类和商品实际交付方式设置，不能自动把虚拟商品伪装成实物/自提。

## 发布

发现 `publish_publish_single` schema，校验完整 payload。常见必填为 `account_id/title/description/price/images`；schema 只校验结构，不能证明分类、素材、库存和平台规则正确。用户只要求草稿/只读测试时停在本地草稿与参数预览。

已有授权应明确账号、商品草稿版本、价格/数量和发布数量上限；缺少授权时展示这个具体草稿再请求。首次真实发布宜一条：

1. 先按 [账号商品同步与查询](catalog-sync.md) 同步目标账号，结合本次平台列表与本站发布日志检查重复商品/相同业务操作。本地没有记录不能证明闲鱼未发布，同步失败不能作为重新上架的依据。
2. 使用 [执行与恢复](execution.md) 中的稳定编号执行 `publish_publish_single`。
3. 保存响应的 `item_id/item_url/log_id/sync_status/sync_message`。
4. 若取得 `item_id` 但 `sync_status` 失败，商品可能已经上架，只补查/同步该商品，不要再次 publish。
5. `items_get_item_detail`（`path.cookie_id`、`path.item_id`）读取本地库。先确认发布后的同步实际完成，再结合本次平台返回和发布日志核对归属、标题、价格及状态。缓存中暂无商品时按 schema 调账号商品同步工具；不能把本地同步失败说成外部未发布。
6. 商品真实存在且交付内容已验证后，按已批准范围绑定卡券，再读取关联结果。

## 批量

`publish_publish_batch` 的 `account_ids × material_ids` 是组合发布，先算总数量和重复风险，不能把两个数组误以为一一配对。沿用授权数量上限，返回 `batch_id` 后用 `publish_get_batch_status` 查询每条结果。成功的商品逐条保存并跳过；部分失败时不重发整个批次。

`ai_listing_create_task` 可能使用站内配置的付费模型。只有费用和范围已批准时才选它；当前 AI 已生成草稿时可以直接用基础素材/发布工具。

验收分别报告：草稿已保存、发布请求已提交、平台商品已生成、本地同步已完成、卡券关联已完成。不得合并为一句模糊的“全部上架成功”。
