# 选品与需求验证

目标是依据真实商品样本找到值得小规模验证的需求，明确能交付什么及如何验证成交。推荐前先查接口；累计想要数、搜索排名和竞品标价不直接等于销量、收入或跟卖收益。

## 何时查询

- 用户让你选品、研究同行或比较哪些虚拟商品有需求：读取当前经营范围及可交付资源，通过现有 MCP 搜索后再推荐，不只给经验清单。同轮已有匹配范围、记录时间且仍有效的真实回执可复用；明确要求离线分析或仅讨论方案时说明证据日期与缺口，不重复查询。
- 查询本人商品、价格、库存、在售状态时转到 [账号商品同步与查询](catalog-sync.md)。市场搜索不替代本人商品同步；已有商品编辑、补库存或发货也不自动增加选品步骤。
- 按 [商品合规与处罚处理](compliance.md) 核对候选的准入、素材权利及交付。本项目已排除范围及处罚记录继续适用；未核实的内容只能作为研究候选，搜索可见不等于可以复制出售。

## 调用与样本范围

1. 复用接入检查及实时 schema，优先调用只读工具 `search_search_items`（`xianyu:read`）。按实际使用场景选少量关键词，先跑通一页；有必要再扩大词或页数。输入示例：

   ```json
   {"body":{"keyword":"小店进销存表格","page":1,"page_size":30}}
   ```

   参数以实时 schema 为准。当前实现使用本站用户自己的第一个 active 账号，不能传一个不存在的账号参数或声称已指定搜索身份；需要指定账号或其他筛选时先核验可用工具及其身份字段。
2. 检查业务 `success`、错误码和实际列表，不能只看 HTTP/MCP 调用成功。保存关键词、采样时间、页码、实际返回条数及私有原始回执。登录失败、依赖缺失、超时、风控或 `verification_required` 不是零需求；停止本轮无依据重试，交还用户完成验证，不换账号绕过。
3. 按商品 ID 去重，保留价格、卖家、发布时间、来源链接和人数证据；同商品命中多个关键词时保留这些来源，但不重复累计。不要只保留最热门结果后计算“平均市场需求”。当前服务会在捕获的一页内按想要数排序并截取 `page_size`；实测曾捕获 30 条而只返回 20 条，`total` 是本次捕获数量，不是全市场总量。根据返回核对是否截断，不能假定每页固定 30 条或分页必定完整。
4. 查询受登录态、搜索词和平台排序影响，注明样本范围。只发起有界、顺序查询；持续采集须有相应授权及资源边界，并核对平台允许的数据获取/使用方式。自封装 MCP 不等于平台开放授权，低频也不自动代表合规。

## 想要数的证据与缺失值

| 字段/情况 | 分析时的处理 |
| --- | --- |
| `want_count` 与原始“人想要”标签一致 | 记录解析值、原始标签和来源路径；它是平台显示的累计关注信号 |
| `raw_data.data.item.main.exContent.fishTags` 的标签，或 `clickParam.args.serviceUtParams` 中的 `args.content` | 可用于交叉核对；结构随版本变化，以实际返回为准，不能从商品标题/卖家宣传文字提取统计 |
| `clickParam.args.wantNum` | 不能单独作为依据：2026-10-28 实测同一商品此字段为 0，但标签和 `want_count` 为正数 |
| 无标签、字段缺失或数字来源不明 | 分析结果设为未知（`null`），同时保留 API 原值；当前解析器可能默认回落为 0，不能据此断定无人想要 |
| 标签为“1.2万人想要”等缩写 | 保留原文，并标记换算为近似值；不能声称精确到个位 |
| API 值与原始标签矛盾 | 标记待核实，先保留回执并检查解析，不能静默选较大的数字 |

统计有效覆盖数（例如“有可核对标签的商品数/样本总数”），未知值不混入零值均值或排行。公开 API 本身未因这份 Skill 改变返回格式；以上是分析层处理要求。

建议保存：`keyword`、`page`、`observed_at`、`item_id`、`source_url`、`price`、`publish_time_reported`、`want_count_api`、`want_count_verified`、`want_label`、`want_count_source`、`want_count_status`（verified/approximate/unknown/conflict）及原始回执位置。账号凭证与业务样本存到 Git 忽略的私有运营目录，不写入公开技能包。

## 从关注度到候选

- 有多个时期的同 ID 快照时，按可比时间间隔观察想要数增量，并比较多个独立卖家是否都有增长。只有一次查询就明确写“当前累计数”，不能生成日增量或趋势。
- 新 ID 建新基线；下一次没有搜到记为未观测，不能填 0 或认定下架。数字下降、标签精度变化、商品内容/价格变化单独记录；累计数除以上架天数只作粗略历史描述，不当作近期增长。
- 比较具体买家问题、同类价格、同质化、制作/维护及售后成本。高关注商品可能是长期积累、低价引流或组合规格，标价不代表真实成交价。不能仅按最大想要数决定照搬上架，也不从搜索结果推算独立买家数。
- 推荐至多三个候选并优先推荐一个，说明证据、交付内容、能做出的差异、素材权利、尚未确认的准入及最低成本验证办法。选品方法复用，具体热卖商品和价格留在当次记录，不固化为长期规则。

## 小规模验证与收益

先做一个可用交付样例，再在明确批准的商品和账号范围发布。验证计划应给出时间、投入上限、数据和继续/调整/停止信号；不要擅自开定时采集、自动跟卖、发卖家私信、下单购买或新增付费服务。发布、卡券、AI 回复及付款后交付沿用已有专项流程，不把调研授权扩展为上架授权。

复盘优先看自己的有效咨询、真实付款、退款、发货失败和售后耗时；能获得时再看曝光/访问。曝光不足、访问后无付款和交付后退款需分别排查，不因观察期内零订单就断言没有需求；不同账号分别记录，每轮尽量只改一个主要因素。

收入按可核验金额计算：商品实收（扣退款）＋已确认推广结算－平台费用－直接成本，另外记录投入时间和共用成本。净额缺数据就标为估算/未知，不保证盈利。网盘拉新需核对用户实际活动的渠道、资源、归因和结算规则；闲鱼订单数不等于有效拉新数，其他渠道的佣金不能套用。只能取得账号级结算时，就按账号对账，不编造单品归因。

交付应包含查询时间与范围、真实样本/人数证据、数据限制、候选取舍及最小验证计划。仅验证接口时报告是否能返回商品与人数即可，不把任务扩展为完整市场调研。接口受阻时报告阻塞和已有证据；只有累计数时不宣称已证明需求增长或销量提升。
